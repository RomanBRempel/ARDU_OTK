# ARDU_OTK — базовые директивы

Эти правила обязательны для всех агентов, работающих в этом репозитории (основной агент и любые субагенты).

## Принцип корневой причины

**Всегда следуй принципу корневой причины: не лечи симптомы, лечи болезнь.**

Перед тем как предлагать любое решение, исправление или изменение — обязательно проведи цепочку «Почему?»
минимум до 3–5 уровней, пока не дойдёшь до системной/процессной причины (а не до ближайшего симптома).

### Правило остановки

- Если дальше «почему» упирается в физику, математику или внешние ограничения, которые нельзя изменить — останавливайся.
- Если причина всё ещё «человек забыл / не сделал / не написал» — копай глубже (почему не было процесса, контроля,
  инструкции, автоматизации).

### После нахождения корневой причины

1. Сначала коротко назови её (1–2 предложения).
2. Потом предложи минимальное изменение, которое устраняет именно эту корневую причину.
3. Только после этого можно упомянуть временные/симптоматические меры (если они нужны).

### Чего делать нельзя

- Останавливаться на первом-втором «почему».
- Предлагать «просто заменить/добавить/починить X» без объяснения, почему это не повторится.
- Расписывать длинную цепочку в ответе пользователю. Цепочку держи в рассуждении, наружу выдавай только
  корень + решение.

### Формат ответа при использовании принципа

```
Корневая причина: …
Что меняем (чтобы устранить корень): …
(опционально) Временная мера: …
```

### Границы применения

Анализ корневой причины выполняется всегда. Само изменение, устраняющее корень, вносится **только по согласованию
с пользователем**, если оно выходит за рамки поставленной задачи.

## Граф знаний — первая точка входа (обязательно)

**Перед любой работой с кодом сначала смотрим граф `graphify-out/graph.json`, а не перебираем репозиторий файл
за файлом.** Это правило обязательно и для основного агента, и для всех субагентов.

Причина: сплошной перебор кода — это восстановление уже известной структуры заново на каждой задаче. Структура
уже извлечена и хранится в графе; перебор тратит контекст, теряет связи между модулями и приводит к правкам
«по одному найденному файлу» вместо правок по реальной цепочке зависимостей.

### Порядок работы

1. **Ориентация по графу.** `/graphify query "<вопрос>"` — найти релевантные узлы, сообщества и связи.
   Для конкретной сущности — `/graphify explain "<Имя>"`, для связи между двумя — `/graphify path "<A>" "<B>"`.
2. **Точечное чтение.** Открыть только те файлы, на которые указал граф (`source_file`, `source_location`).
3. **Проверка полноты.** Если граф не покрывает нужную область — искать `Grep`/`Glob` целенаправленно
   по конкретной гипотезе, а не читать каталог целиком.
4. **Обратная связь.** Если при чтении обнаружена связь, которой нет в графе, — это признак устаревшего графа,
   см. раздел ниже.

### Чего делать нельзя

- Начинать задачу с рекурсивного чтения `ARDU_OTK/**` или `Get-ChildItem -Recurse` «чтобы понять проект».
- Читать файл целиком, если граф указал на конкретный узел и его расположение.
- Игнорировать граф на том основании, что «так быстрее» — при существующем `graphify-out/graph.json`
  это не быстрее, а дороже по контексту.

### Когда граф можно не открывать

- Задача целиком в одном уже открытом файле и не затрагивает связи с другими модулями.
- Тривиальная механическая правка (текст, форматирование, версия).
- `graphify-out/graph.json` отсутствует — тогда сначала построить граф: `/graphify .`

## Актуальность графа знаний (graphify)

**Граф в `graphify-out/` — локальный кэш, в git его нет (`.gitignore`). Он обновляется, когда его собираются
читать, а не после каждой правки.** Обновлять граф в той же задаче, что и изменение, не нужно.

Причина: кэш инвалидируется на стороне чтения. Пересборка после каждой правки или коммита тратит время на граф,
который до следующей сессии никто не откроет, а граф в git превращал каждую правку кода в правку артефакта
и шум в истории.

### Как граф остаётся свежим

| Механизм | Что делает |
|---|---|
| Хук `SessionStart` | Сверяет `manifest.json` с корпусом. Если разошёлся код — сам запускает фоновый `graphify update .` (AST, без LLM, лог `graphify-out/refresh.log`) и сообщает, по каким файлам граф пока недостоверен |
| Хук `PostToolUse` на `Write` | Помечает созданный файл как непокрытый графом |
| Вручную | `python tools/graph_freshness.py` — проверка; `--refresh` — синхронно обновить код графа |

### Когда обновлять вручную

Только когда это нужно текущей задаче:

| Ситуация | Команда |
|---|---|
| Изменены документы (`.md`, `.yml`, `.png`) и задача опирается на их смысл | `/graphify . --update` |
| Массовые переименования, перемещения, удаление модулей | `/graphify .` (полная пересборка) |
| Нужны только новые сообщества/кластеры | `/graphify . --cluster-only` |
| `graphify-out/` отсутствует (новая машина, свежий клон) | `/graphify .` |

### Как читать предупреждения

- **Расхождение** — по перечисленным файлам граф недостоверен: читай их напрямую. Это не повод прерывать задачу.
- **Целостность** (висячие рёбра, петли, дубликаты) — граф пригоден, но о дефекте сообщить пользователю, не скрывать.
  Петли вызовов из AST (перегрузки, рекурсия) дефектом не считаются и упоминаются справочно.
- Отвечать на вопросы об архитектуре по графу, который заведомо устарел в нужной области, нельзя — сначала
  обновить его или прочитать файлы напрямую.

Границы механизма: изменённые документы фоновым обновлением не покрываются — им нужно семантическое извлечение
(LLM), поэтому о них хук только сообщает.
