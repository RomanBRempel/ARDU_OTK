# ARDU_OTK — базовые директивы

Эти правила обязательны для всех агентов, работающих в этом репозитории (основной агент и любые субагенты).

## Принцип корневой причины

**Всегда следуй принципу корневой причины: не лечи симптомы, лечи болезнь.**

Перед тем как предлагать любое решение, исправление или изменение — обязательно проведи цепочку «Почему?»
минимум до 3–5 уровней, пока не дойдёшь до системной/процессной причины (а не до ближайшего симптома).

### Правило остановки

- Если дальше «почему» упирается в физику, математику или внешние ограничения, которые нельзя изменить — останавливайся.
- Если причина всё ещё «человек забыл / не сделал / не написал» — копай глубже (почему не было процесса, контроля,
  инструкции, автоматизации).

### После нахождения корневой причины

1. Сначала коротко назови её (1–2 предложения).
2. Потом предложи минимальное изменение, которое устраняет именно эту корневую причину.
3. Только после этого можно упомянуть временные/симптоматические меры (если они нужны).

### Чего делать нельзя

- Останавливаться на первом-втором «почему».
- Предлагать «просто заменить/добавить/починить X» без объяснения, почему это не повторится.
- Расписывать длинную цепочку в ответе пользователю. Цепочку держи в рассуждении, наружу выдавай только
  корень + решение.

### Формат ответа при использовании принципа

```
Корневая причина: …
Что меняем (чтобы устранить корень): …
(опционально) Временная мера: …
```

### Границы применения

Анализ корневой причины выполняется всегда. Само изменение, устраняющее корень, вносится **только по согласованию
с пользователем**, если оно выходит за рамки поставленной задачи.

## Граф знаний — первая точка входа (обязательно)

**Перед любой работой с кодом сначала смотрим граф `graphify-out/graph.json`, а не перебираем репозиторий файл
за файлом.** Это правило обязательно и для основного агента, и для всех субагентов.

Причина: сплошной перебор кода — это восстановление уже известной структуры заново на каждой задаче. Структура
уже извлечена и хранится в графе; перебор тратит контекст, теряет связи между модулями и приводит к правкам
«по одному найденному файлу» вместо правок по реальной цепочке зависимостей.

### Порядок работы

1. **Ориентация по графу.** `/graphify query "<вопрос>"` — найти релевантные узлы, сообщества и связи.
   Для конкретной сущности — `/graphify explain "<Имя>"`, для связи между двумя — `/graphify path "<A>" "<B>"`.
2. **Точечное чтение.** Открыть только те файлы, на которые указал граф (`source_file`, `source_location`).
3. **Проверка полноты.** Если граф не покрывает нужную область — искать `Grep`/`Glob` целенаправленно
   по конкретной гипотезе, а не читать каталог целиком.
4. **Обратная связь.** Если при чтении обнаружена связь, которой нет в графе, — это признак устаревшего графа,
   см. раздел ниже.

### Чего делать нельзя

- Начинать задачу с рекурсивного чтения `ARDU_OTK/**` или `Get-ChildItem -Recurse` «чтобы понять проект».
- Читать файл целиком, если граф указал на конкретный узел и его расположение.
- Игнорировать граф на том основании, что «так быстрее» — при существующем `graphify-out/graph.json`
  это не быстрее, а дороже по контексту.

### Когда граф можно не открывать

- Задача целиком в одном уже открытом файле и не затрагивает связи с другими модулями.
- Тривиальная механическая правка (текст, форматирование, версия).
- `graphify-out/graph.json` отсутствует — тогда сначала построить граф: `/graphify .`

## Актуальность графа знаний (graphify)

**Граф в `graphify-out/` — часть артефактов репозитория. Если изменение попадает в список ниже, граф обязан быть
обновлён в той же задаче, что и само изменение, а не «когда-нибудь потом».**

Причина жёсткости правила: граф — это кэш структуры проекта. Кэш без правила инвалидации молча расходится с кодом,
и агент, ответивший по устаревшему графу, выдаёт уверенно неверный ответ. Поэтому триггер обновления привязан
к типу изменения, а не к памяти исполнителя.

### Изменения, которые ломают граф (обновление обязательно)

1. **Состав корпуса** — добавлен, удалён, переименован или перемещён любой файл поддерживаемых типов:
   `.cs`, `.xaml`, `.csproj`, `.slnx`, `.json`, `.md`, `.yml`/`.yaml`, `.png`, `.py`.
   Список здесь — ориентир для человека; `tools/graph_freshness.py` берёт фактический набор типов
   из `graphify-out/manifest.json`, поэтому не расходится с инструментом, даже если список выше отстал.
2. **Структура кода** — новый/удалённый/переименованный класс, интерфейс, метод, свойство, namespace;
   изменение `using`-ов; изменение сигнатуры публичного API.
3. **Связи между модулями** — новые вызовы между сервисами, изменение регистрации/внедрения зависимостей,
   изменение `x:Class` или привязки XAML к code-behind, новая страница/навигация.
4. **Зависимости сборки** — правка `PackageReference`/`ProjectReference` в `.csproj`, `Directory.Build.props`,
   состава проектов в `.slnx`.
5. **Смысловой слой документации** — правки, вводящие или переопределяющие понятия и правила:
   `README.md`, `AGENTS.md`, `CLAUDE.md`, `.github/skills/**`, `.github/workflows/*.yml`.

### Изменения, которые граф НЕ ломают (обновление не требуется)

- Форматирование, отступы, переносы строк.
- Комментарии и правки текста внутри тела метода без новых вызовов и типов.
- Изменение литералов, констант, строк локализации.
- Бамп версии, правка `.gitignore`, содержимое бинарных ассетов без переименования.

### Как обновлять

| Ситуация | Команда |
|---|---|
| Изменены/добавлены отдельные файлы (обычный случай) | `/graphify . --update` |
| Массовые переименования, перемещения, удаление модулей | `/graphify .` (полная пересборка) |
| Файлы не менялись, нужны только новые сообщества/кластеры | `/graphify . --cluster-only` |

### Порядок действий

1. Внести изменение в код или документацию.
2. Если изменение попадает в список ломающих — обновить граф соответствующей командой.
3. Проверить целостность: `python tools/graph_freshness.py`. Строка о целостности означает висячие рёбра,
   петли или дубликаты — граф остаётся пригодным, но о дефекте сообщить пользователю, не скрывать.
4. Отвечать на вопросы об архитектуре только по актуальному графу; если граф заведомо устарел — сначала обновить,
   потом отвечать.

Проверка целостности намеренно оформлена как код, а не как поиск подстроки в отчёте. Прежняя редакция пункта 3
предписывала искать текст предупреждения в `GRAPH_REPORT.md`, куда graphify его не пишет вовсе: предупреждение —
это вывод отдельного шага скилла в stdout. Проверка не срабатывала никогда, а после индексации самих директив
начала срабатывать ложно — на собственную формулировку правила, попавшую в граф как узел.

### Чем это правило подкреплено

Правило выше — инструкция, а инструкция полагается на память исполнителя. Поэтому расхождение графа с кодом
дополнительно ловится механически, проверкой `tools/graph_freshness.py`. Она сверяет `graphify-out/manifest.json`
с корпусом на диске и вызывается из трёх точек:

| Точка вызова | Что закрывает |
|---|---|
| Хук `SessionStart` | Сессия начинается с честной сводки расхождений, до того как агент поверит графу |
| Хук `PostToolUse` на `Write` | Созданный файл сразу помечается как непокрытый графом — иначе модуль остаётся невидимым |
| CI `graph-freshness` | Устаревший граф не попадает в `main` и не наследуется следующими сессиями |

Локально признаком устаревания служит `mtime`, в CI — время коммитов (после `checkout` все `mtime` одинаковы).
Проверку можно запустить и вручную: `python tools/graph_freshness.py`.

**Если проверка сообщила о расхождении — сначала обнови граф, потом отвечай по нему.** Предупреждение из хука
не является поводом прервать текущую задачу: оно означает, что по перечисленным файлам граф недостоверен и
их нужно читать напрямую.

Границы механизма: переименования и удаления, сделанные в обход инструмента `Write` (например `git mv` из
командной строки), в момент операции не отлавливаются — их ловит `SessionStart` при следующем запуске и CI.
